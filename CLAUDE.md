# Boat Race with 99 Engine

## Repos
- Frontend (this repo): `C:\ThreeJS\Boat-race-with-99-engine\Boat-race-with-99-engine`
- Backend: `C:\ThreeJS\Boat-race-with-99-engine\Boat-race-with-99-engine-backend` (Colyseus + MongoDB game server, see its CLAUDE.md; the frontend's only link to it is `src/net.js`). "Backend" always means this folder; "frontend" means this repo.
- Reference game for Bloxity patterns: `C:\ThreeJS\Clean-leaves-for-loot\Clean-leaves-for-loot` (the avatar/ and bloxity.js code here was ported from it).

Three.js (vanilla, no React) + Vite + Rapier (`@dimforge/rapier3d-compat`, wasm inlined; `main.js` awaits its init at top level, hence `build.target: 'es2022'`). The scene is the race lobby, rebuilt to match the user's reference screenshot (third-person view, no UI/HUD): a cracked-sand beach with the START gate at the shoreline (north view, -Z), the training plaza under the cliffs (south view, +Z), the Eggs stall past the statue wall (east view, +X) and the Boats stall (west view, -X), and the player standing in an engine boat. The four reference shots were taken from around the spawn; keep all four views in mind when moving anything (e.g. the west Boats stall is also the green boat + pink strip at the right of the south view). The HUD (`src/hud.js` + `hud.css`, SVG icons in `src/hudIcons.js`, values/progress-bar tiers in `HUD` in config) recreates the user's in-race reference screenshot: logo + menu/chat pill, race timer, Once a Day, six round buttons, CLAIM + 8 menu tiles (each calls `actions.<name>` passed to `createHud` in main.js, e.g. `rebirth`, `pets`), Season/Ready/x20 promos, trophies/wins/gems pills (`hud.setStat`), AUTO TRAIN/RACE toggles, boosts, chat unread badge (`hud.setChatUnread`), 1st/2nd/3rd podium under the timer (top three by distance), two-slot hotbar (1/2), three-row distance bar (0..2K / 2K..13K / 13K..2.5M = the finish, rows and `to` values in `HUD.progress`) with every racer's head placed by distance (`hud.setDistance(d)` for the player, `hud.setRacers([{ id, name, distance, look, pfp }])` for the rest = the remote players racing right now (net.js `remoteRacers()` off the server roster, refreshed by race.js 10x/s even in the lobby; each racer's Bloxity `pfp` once loaded, else a cartoon `head(look)` from `HUD.racerLooks` picked by session id); the player's own marker and podium face use `hud.setPfp(bloxity.getPfp())`; the podium hides when nobody else is racing). Sizes are reference pixels x `--u` (= screen / 1920x992, clamped by `HUD.minScale`); on touch every control grows to 44 px, and there are portrait (3x2 round buttons, timer under the logo, bars lifted above JUMP) and phone-landscape (`.short`: flowing top row, split right column) layouts; it hides touch.js's top-right buttons (the HUD menu covers them). HUD z-index 20, popup windows 100. (textures.js painters for grass/tiles/crates/planks are unused leftovers.) Layout is Roblox-scale and was measured off the reference by back-projecting pixels: the gate is ~38 m wide, ~50 m ahead of the spawn, and the chase cam is low (~8 deg tilt). Everything is procedural (canvas textures); the only imported model is the Bloxity base rig `public/avatars/player.glb`. Font: Fredoka.

- `npm run dev` / `npm run build`. `VITE_DEV_MODE=true` (see `.env.example`) skips the Bloxity SDK/CDN. Deploy: `.github/workflows/deploy.yml` uploads `dist/` to Bloxity Hosting (main = prod, dev = dev channel).
- All tunables are in `src/config.js`. All Bloxity SDK calls go through `src/bloxity.js` and must never throw (SDK may be blocked). Feet position is `player.position`; `player.renderPosition` is interpolated for drawing. Falling below `PHYSICS.killY` respawns.

- Rebirth: `src/rebirth.js` + `rebirth.css`, the "Rebirth!" window (HUD Rebirth tile / B). A rebirth spends all energy (lightning) for +`REBIRTH.boostPerRebirth`% boost; cost `baseCost * costGrowth^n`; AUTO REBIRTH fires whenever energy reaches the cost. State `{ rebirths, energy, auto }` saved by the server (see Saves). The energy IS the player's lightning: one counter, shown on the HUD's bolt pill (`createRebirth({ onChange })` mirrors it into `hud.setStat('wins')`) and read as race speed; a new player starts with `REBIRTH.startEnergy` (121). Training and bolt gifts add it, trail purchases spend it (`addEnergy(-n)`), a rebirth zeroes it (speed back to the base). `__game.rebirth.addEnergy(n)` in dev.

- Boosts: `src/boosts.js` wires every system's values into gameplay. `boostSources()` = one row of % per equipped source: engine (wins/acc/train, x the equipped boat's `engines` count), boat (wins/luck/acc), partner (wins/luck/acc), trail (wins/acc; even the free White is +50/+50), rebirth (`boostPerRebirth` % to wins + train). `boosts()` combines: `wins` = (1 + sum wins %) x the pets' boost (race Wins), `acc` = 1 + sum acc % (race acceleration), `speed` = 1 + `RACE.accSpeed` x acc % (top speed multiplier; starter gear raft 20 + basic engine 11 + White 50 = +81%: 145 -> 262), `train` = 1 + sum train % (training), `luck` = sum luck %, `lucky` = luck / (luck + `RACE.luck.half`) capped at `max` (chance a checkpoint pays double: "LUCKY x2!" on the reward popup). race.js reads it at race start, training per tick. A race that starts faster than the previous one shows "Top Speed 145 -> 262!" (`raceHud.speedUp`). The HUD's three boost circles (`actions.boosts`) open the "Boosts!" window (`src/boostPanel.js` + `.css`, shared window shell): a table of every source x Wins/Acc/Luck/Train, the pets' multiplier, totals, and four tiles (Race Wins x, Top Speed +%, Lucky x2 %, Training x); portrait = icon-only headers, wrapping names, 2x2 tiles.

- Saves: progress lives ONLY on the server (`../Boat-race-with-99-engine-backend`); never write progress to localStorage/sessionStorage (the only browser keys are the guest/dev id in net.js and audio's mute setting). `src/net.js` (Colyseus SDK, room `world`, after Kayak & Surf's): `initNet({ hud, stores })` in main.js, where every store (rebirth, pets, engine, boats, partner, gifts, trails, race, eggs) has `snapshot()` (its part of the save) and `hydrate(doc)` (resets to a new player's state, takes its part, re-renders/re-equips). On join the server answers `progress` (hydrate everything), `noProgress` (new account / guest / no DB: keep the fresh state and save it) or `serverError` (saving stays off). net.js polls the whole snapshot every second and sends `saveProgress` when it changed, at most every `NET.saveEvery` s, plus on hide/pagehide, so a new saved field only needs adding to a store's snapshot/hydrate and the backend's `sanitize.ts`/`PlayerDoc`. Guests (no Bloxity sign-in) are never saved: their progress lasts the page. Server URL: built games (prod and the dev channel) always go through the Bloxity matchmaker (`resolveServerEndpoint` in bloxity.js = `Legion.SDK.net.resolveEndpoint`, a new Client per resolve; never connect to `<id>.host.bloxity.io`); only `npm run dev` uses `SERVER_URL` (`VITE_SERVER_URL_DEV`, default `ws://localhost:2567`). Checkpoints (`RACE.checkpoint`): pale see-through walls across the lane (a pool of `ahead` meshes placed relative to the boat; the last one passed stays until it is behind the camera). Spacing is picked per race from the top speed: the `steps` value nearest (log) to top x `seconds` (7 s; 145 -> 1K, 745 -> 5K), after the `early` ones (10..500) below that step. A checkpoint pays max(1, floor(min(studs, top x `paySeconds`) x step / 1M)) Wins (9K at a 1K step -> +9; an early one 1) x the Wins boost: quadratic for the first 45 s of distance, then flat per checkpoint, so Wins per hour match the old 90 s races at any speed (a new player's full 2.5M race ~29K) instead of growing with the square of a 2 h race; "Next 🏆+N at 9K" under the studs callout (`raceHud.setNext`) shows the next one. ## Mobile & responsive (required for every change)
The game must play on phones and tablets (portrait and landscape) as well as desktop. Treat a feature as unfinished until it works on touch and on a small screen.
- **Input**: every action needs a touch path, not just a key. Use Pointer Events (`pointerdown/move/up`, check `e.pointerType`), never mouse-only events. Layout (implemented in `src/touch.js`): left-thumb virtual joystick -> `inputState.move`, right-side drag -> `inputState.look`, on-screen buttons for jump/sprint/mode/etc., pinch -> `inputState.zoom`. Everything still feeds `inputState` in `src/input.js` so game code stays input-agnostic. Pointer lock does not exist on touch; never rely on it.
- **Detection**: decide touch UI with `matchMedia('(pointer: coarse)')` / `navigator.maxTouchPoints`, not the user agent. Show touch controls only on coarse pointers; a device can have both.
- **Layout/UI**: HUD and menus use relative units (`%`, `vw/vh`, `dvh`, `clamp()`) and flexbox/grid, no fixed pixel layouts. Tap targets >= 44px. Respect notches with `env(safe-area-inset-*)` (viewport already has `viewport-fit=cover`). Text readable at 360px width. No hover-only interactions. Add `touch-action: none` on the canvas and game controls so the browser does not scroll/zoom.
- **Resize/orientation**: anything sized to the screen (camera aspect, renderer, HUD) must react to `resize` (covers orientation changes). Use `visualViewport` where the on-screen keyboard or browser bars matter.
- **Performance**: mobile GPUs are weak. Respect the `graphics_quality` presets in `src/config.js` (cap DPR, shadow map size, draw distance); default to a lower preset on coarse-pointer devices. Avoid per-frame allocations; keep draw calls and texture sizes low.
- **Testing**: check every UI/input change at a phone viewport (e.g. 375x812 and landscape 812x375) with touch emulation, plus desktop, before calling it done.
